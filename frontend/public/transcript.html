The user declared these as **mandatory, standing rules for every future RAG/ingestion change** in this project (stated 2026-09-02, after finding real bugs from violating them): "Make the above prompt given by me as a mandatory logic from now what we do in setuping RAG."

**Rule 1 — only topics are stored as topics, never subtopics.**
Per SPEC.md's chunking design: extract three things per chapter — chapter name, topic names, and each topic's content.
- If a topic's content is small enough to fit a normal chunk size, store it as ONE topic-level chunk.
- If a topic's content is larger than a chunk, split it into subtopics for chunking purposes, then chain those subtopic chunks back together under the SAME topic (topic_number stays the topic's own number, subtopic chunks are just sequential chunk_index entries under it) — subtopics must never be promoted to their own topic entry.
- **Bug this rule was written to prevent** (found in production before this rule existed): a large topic's subtopics were being stored as if they were their own topics, so in the app, selecting a chapter showed subtopic names polluting the topic list instead of just the real topic names.
- **How to apply:** any time chunk_topics.py / detect_headings.py logic is touched, verify large-topic subtopic chunks still report the parent topic's name/number, not the subtopic's own heading, in `topic`/`topic_number` fields.

**Rule 2 — content before the first real topic heading is "Introduction," not a bracketed label or stray text.**
Whatever chapter-opening content appears before the first detected topic heading should be labeled with the plain name "Introduction" — not left as some other bracketed/placeholder string.
**How to apply:** check `clean_topics()`/`detect_topics()` in `detect_headings.py` for what it currently names this leading span, and fix if it's not literally "Introduction".

**Rule 3 — no single generic extraction heuristic across all textbooks; build/verify per-textbook.**
Restated multiple times by the user (first raised for class 10 Social Science's 4 sub-books, now made a general standing rule for ALL textbooks, not just Social Science): different NCERT textbooks have different page-layout/heading designs, so topic/heading detection must be verified — and where needed, given book-specific logic — per textbook, not assumed to generalize from one design to all.
**How to apply:** when starting extraction work on a textbook, first inspect that specific book's actual heading hierarchy/typography (font sizes, colors, numbering conventions) rather than assuming the existing shared heuristic already handles it correctly. Go through textbooks one at a time (the user's own words: "We will go by textbook to textbook").

**Process note:** the user wants to be walked through each textbook's extraction design before implementation — "I will travel with you" — and wants to be asked whenever there's a genuine judgment call ("If you have any doubts in middle about should i consider this or skip this ask me"). `detect_headings.detect_topics_ss_revised_curriculum` implements the shared font-size-tiered detector (17pt=topic, 15pt=subheading-chains-under-parent, 14pt=callout-box-label-not-a-heading). Progress: **class 6 done** (2026-09-02, all 14 chapters, 1 known residual — an atypical bundled front-matter file). **Class 7 done same day** (all 20 chapters, zero residual — needed a "LET'S REMEMBER" activity label, an exercises-header text variant, and a real bug fix: a lettered subheading marker rendering at topic size in one chapter, fixed generally via a lettered-marker-forces-subheading override + same-block-continuation-ignores-tier-mismatch). **Class 8 done same day** (all 15 chapters, zero residual — one bug: two superscript "th" ordinal suffixes in a chapter title with a date range land at the same row position and merge into "thth" via this pipeline's row-based glyph-dedup, landing in the topic size range and swallowing the Introduction; fixed by rejecting any bare ordinal suffix, including concatenated copies, as heading text). **Class 9 done same day — last book in this production family** (all 9 chapters, zero residual — a differently-designed title page needed no fix since it lands outside heading-size ranges regardless, and the callout-box system isn't used in this book at all; one bug: a heading above a table whose text reads out of order ahead of it, per the pre-existing table-layout limitation, left with nothing but a page-footer line — fixed by raising the empty-topic filter to a minimum content length of 80 chars, confirmed safe against classes 6-8's full regression). **Maths and Science done same day (2026-09-02) — the last remaining subjects, closing out the full-corpus audit.** Unlike Social Science, this wasn't a wrong-architecture problem (the "N.M Heading" numbered design is correct for every Maths/Science book) — it was five narrower bugs in the shared production path (`extract_exercises.clean_topics()`) that had been shipping wrong data the whole time, undetected because nothing had checked its output against the mandatory rules chapter-by-chapter before: (1) decimal numbers in body text/tables (e.g. "37.0 °C") coincidentally matching the heading regex shape at sizes above the old single global `MIN_HEADING_SIZE=12.0` floor, fragmenting real topics — fixed by calibrating each chapter's real heading size empirically (real heading sizes range 12-17pt across book editions, so no single constant works); (2) a decorative icon glyph (`\x07` control character) leaking into topic names, pervasive in class 8 Science — fixed by stripping control characters; (3) one real topic's content silently absorbed into its neighbor because its own heading was punctuated inconsistently ("2.4." vs "2.4", class 9 Maths ch2) — fixed by tolerating an optional trailing period; (4) title-page furniture (a stray digit, repeated chapter number/title) stored as "Introduction" — fixed with the same 80-char minimum used for Social Science; (5) class 10 Science ch7's title extracted as "B" (a decorative drop-cap letter the same size as the real title) — fixed by extending an existing single-letter-drop-cap guard to the tier that was missing it. All fixes verified against previously-correct chapters with zero regressions. **Confirmed non-issues, not fixed:** a book's own real first section sometimes IS titled "N.1 Introduction" (universal older-NCERT convention, e.g. every class 10 Maths chapter) — harmless since `app/catalog.py` groups topics by name, not number; class 7/8 Maths each bundle two textbook "Parts" that both restart chapter numbering at 1 — harmless since chapter_number is documented as sort-order-only, never identity; class 8 Maths ch2 has a genuine source-book typo (two different topics both numbered "2.5") — left as-is, correctly reflects what the book prints. **Result:** all 131 chapters re-ingested (1866 chunks, down from 1933 — pollution removed), chapter title cache corrected, full backend test suite passes (143 tests). **Same-day follow-up: the user caught a 6th bug (wrong class 9 Maths chapter 8 title) that the audit above missed, and fixing it required real care not to introduce new regressions.** The chapter-title extraction code (`_looks_like_title_candidate` / `_color_banner_title_and_number` in `schema.py`) had a 60-char length cap that rejected this book's real 66-char title, leaving a same-colored recurring feature-box label ("Think and Reflect") to win by default. Raising the cap to 80 immediately exposed a second, latent bug: a same-color "pick the larger candidate" tie-break (needed to resolve the real-title-vs-label case) was too eager whenever a title's own first letter renders as an enlarged same-colored drop-cap — nearly every class 10 Maths chapter title broke (dropping its first letter: "Circles"→"Ircles", "Polynomials"→"Olynomials") the moment the pre-existing single-character drop-cap guard (added earlier the same session, for a different bug) rejected the drop-cap letter, leaving its ALL-CAPS remainder to win alone. **Lesson: fixing one bug in a multi-tier heuristic function can silently break a DIFFERENT case the old, buggier behavior was accidentally protecting — after any such fix, re-run a full-corpus regression scan (not just the one reported case) before considering it done.** Root-fixed with a new `_reattach_dropcap_letters()` pass that recombines a drop-cap letter with its spatially-adjacent remainder (same row, touching x, overlapping y — they share a baseline, not a top edge) before any other candidate-selection logic runs; this also solved a multi-word/wrapped-title drop-cap case ("REAL NUMBERS") the code's own comments had previously documented as unsolvable. Verified via a full-corpus tier-0 diff (before vs. after) each time, not just spot checks. `chapter_titles_final.tsv` corrected for class 9 Maths ch8; class 10 Maths never actually shipped wrong data to production because `patch_chapter_metadata.py --all`'s TSV-cache override silently absorbed the transient bug at ingestion time — but the underlying code bug still needed a real fix since new/future chapters wouldn't have that same protection. Full writeup: `ingestion/PARSING_EXCEPTIONS.md` section 2f follow-up.

**Second same-day follow-up: the user caught a batch of wrong class 10 Social Science CHAPTER TITLES (not topics) — 4 already-known-wrong Economics titles left unresolved from an earlier session, plus a genuinely new History bug.** History's first chapter of each of its 3 "Sections" (13, 15, 17) was showing that Section's own descriptive theme name ("Events and Processes") instead of the chapter's real title ("The Rise of Nationalism in Europe") — caused by `_big_font_title` (the page-0/1 title-extraction fallback in `schema.py`) having no way to recognize a "SECTION [roman numeral]" divider page as such, so the Section's own large theme name won outright; a stray "Reprint <year>" printer's watermark then ALSO won as a false candidate on the following blank page. Fixed with: a `_big_font_title` skip for both patterns (matching its existing bare-"CHAPTER" skip), an independent check that discards page 0's candidate entirely (not just strips the marker) when a SECTION divider is present so the fallback correctly cascades to page 1 then a new page-2 tier. The 4 Economics titles ("Sectors"/"Oneyandredit"/"Globalisation"/"Onsumerights") turned out to be TWO different narrow issues — one a size-ratio threshold (0.565 vs the 0.7 cutoff) too book-specific to safely generalize, the other the book's own running-header text being internally corrupted (both words of "MONEY AND CREDIT" losing their own leading letter, then joined with no space) in a way the existing single-dropped-letter recovery heuristic doesn't cover. Both left as direct `chapter_titles_final.tsv` corrections rather than new code generalizations, matching the project's established "don't over-fit a shared heuristic to one book" judgment. Verified via a full-corpus `extract_chapter_meta()` diff (before/after) confirming zero unintended changes elsewhere. `patch_chapter_metadata.py --all` re-run (165 chunks); full backend test suite passes (143 tests). **Third same-day round: the user reviewed the app directly (not asked for another blind audit) and named three concrete, specific problems — this is the most effective way this project finds real bugs, more than any heuristic re-scan.** All three were genuinely different root causes needing genuinely different fixes, reinforcing [[rag-extraction-rules]]'s Rule 3 at an even finer grain than "one architecture per sub-book":
- **History:** the numbered-heading design routed through the generic `clean_topics()` path was silently WRONG, not just unaudited — "N.M" in this book is subsection-of-N, not chapter.section, so every subsection was a promoted sibling topic (a real, previously-undetected Rule 1 violation, hiding behind a design that LOOKED like the familiar numbered-heading case). - **Geography:** a genuinely new failure class for this project — a two-column page layout where PyMuPDF's own block order doesn't respect left-to-right reading order. **Practical technique that worked well:** dump raw span data (size/color/text) directly via `page.get_text("rawdict")` across several sample chapters BEFORE writing any detection logic, to find the book's actual size/color tiers empirically rather than guessing from one chapter. Real headings in every book design seen so far are mixed-case (has a lowercase letter); a same-size ALL-CAPS candidate has consistently turned out to be decorative noise (map/diagram labels), not a heading — worth checking early in any new textbook.

**Operational gotcha — always re-run `patch_chapter_metadata.py --all` after re-ingesting any subject.** Found in production while finishing class 6 Social Science: re-ingesting chunks via `embed_and_store.py` calls `extract_chapter_meta()` per-chapter with no cross-chapter exclusion set, so any chapter that needs the cross-chapter dedup fix (a book/feature-level recurring label like "Big Questions" winning over the real title) silently regresses back to the wrong shared chapter name — multiple real chapters then merge into one bogus chapter bucket in the app's catalog. `patch_chapter_metadata.py --all` is safe and idempotent (reads `chapter_titles_final.tsv`, matched by stable `source_file`) — just always run it as the last step after any re-ingestion, and verify via `app.catalog.list_chapters`/`list_topics` (not just Chroma's raw chunk metadata) since that's what actually catches a merged-chapter regression.

**Rule 4 — topic names (and even chapter names) are NOT globally unique across the corpus; never key data on a bare topic name.**
Found 2026-09-08, auditing the whole project cold: "Introduction" alone is a real topic name shared by 255 different chapters across classes 6-12, and even bare chapter names collide across subjects (e.g. "Thermodynamics" in both Physics and Chemistry, "Biomolecules" in both Biology and Chemistry). `backend/app/catalog.py`'s old `topic_index()` (topic name -> owning chapter, first-write-wins) and `performance_counters` (old PK: `user_id, topic, question_type`) both silently assumed a topic belongs to exactly one chapter — false at corpus scale, which corrupted the dashboard's by-subject/by-chapter rollup and the accuracy-weighted quiz-selection logic for any multi-chapter request spanning colliding topic names (common for "all chapters"/subject-wide quizzes, since "Introduction" repeats in nearly every chapter) and could silently under-cover a chapter (two colliding topics collapsing into one allocation line).
**Fixed 2026-09-08:** `performance_counters` re-keyed on `(user_id, class, subject, chapter, topic, question_type)` (schema.sql migration, auto-drops old rows — their numbers were exactly the contaminated data this fix prevents, nothing trustworthy to migrate); `GradedAnswer`/`grade_answer` now carry `chapter`; `quiz_service._resolve_sub_units` now builds a synthetic per-(chapter,topic) key instead of using the bare topic name as the sub-unit identifier; `topic_index()`/`TopicOwner` removed from `catalog.py` (dead code once `performance_service.py` reads `class`/`subject`/`chapter` directly off `performance_counters` rows instead of reverse-looking-up a topic name). Old `performance_counters`/`get_topic_accuracy` call sites (tests) updated to pass class/subject/chapter explicitly.
**How to apply:** any new feature that groups, filters, or displays by "topic" alone (not paired with at least its chapter) is suspect — check whether two different chapters could plausibly share that topic's name (generic names like "Introduction"/"Summary"/"Classification"/"Nomenclature" are confirmed repeat offenders) before trusting a bare-topic-keyed lookup or aggregate.
